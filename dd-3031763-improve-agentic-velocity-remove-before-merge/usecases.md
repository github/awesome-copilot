| Likely to benefit | Unlikely to benefit |
|---|---|
| A five-issue infrastructure feature with reproducible acceptance tests | Upstream code where AI-generated contributions are prohibited |
| Dependency, platform, or runtime upgrades split into ordered compatibility tasks | Exploratory research where nobody yet knows what should be built |
| Adding an internal service capability across schema, API, implementation, tests, and deployment | A one-line fix that is faster to make and review manually |
| Repository migrations with clear per-step gates and rollback boundaries | Work requiring continuous interactive product or UX decisions |
| Repeated implementation campaigns where each PR builds on the previous merged PR | Changes without meaningful automated tests or substantive CI |
| Work involving ADRs and research spikes whose findings must become precise issue specifications | A very large, indivisible change that exceeds practical review coverage |
| Internal developer tooling, build systems, CI/CD, and infrastructure-as-product work | Repositories where agents cannot access the environment needed to validate completion |
| Campaigns where traceability, retry evidence, and post-mortems matter | Work where the primary bottleneck is deciding strategy rather than supervising execution |
