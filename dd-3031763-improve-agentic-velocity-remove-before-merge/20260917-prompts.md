I would answer MC roughly like this:

That is fair feedback. Shepherd-task is not a general-purpose development workflow, and the workshop should make its applicability boundaries clearer before explaining how to run it.

Its value is not primarily “AI writes code.” It automates the repetitive supervision loop around a sequence of well-specified issues: assigning work, waiting for implementation, approving workflows, checking acceptance criteria and CI, evaluating review findings, applying justified fixes, re-reviewing the changed head, merging serially, and retaining traceable evidence.

For upstream OpenJDK contributions, given your constraint that AI-generated material cannot be contributed, shepherd-task is probably not appropriate for implementing the contribution. Its implementation stages deliberately use CCA and local Copilot to produce and modify code. Even if a human later reviewed or rewrote that code, provenance and policy concerns would make this the wrong workflow unless the applicable OpenJDK rules explicitly permitted it.

It might still inspire non-generative process automation—state tracking, CI gates, evidence capture, or post-mortems—but that would be a different system. I would not recommend running shepherd-task against an OpenJDK contribution and trying to separate acceptable human work from AI-generated work afterward.

Infrastructure treated as a product is a much better fit, provided its repository accepts AI-assisted contributions. Infrastructure work often has exactly the properties shepherd-task expects:

- a GitHub issue backlog;
- independently deliverable, ordered changes;
- strong automated validation;
- clear configuration or behavioral acceptance criteria;
- pull requests that can be reviewed and merged serially;
- expensive but repetitive CI and review supervision.

Jaz or Illuminate might also be good candidates, but only if their work can be decomposed into similarly testable issues and their contribution policies permit the participating AI tools. The project name or language does not determine suitability; the workflow and governance do.

I would then give concrete examples.

| Likely to benefit | Unlikely to benefit |
|---|---|
| A five-issue infrastructure feature with reproducible acceptance tests | Upstream code where AI-generated contributions are prohibited |
| Dependency, platform, or runtime upgrades split into ordered compatibility tasks | Exploratory research where nobody yet knows what should be built |
| Adding an internal service capability across schema, API, implementation, tests, and deployment | A one-line fix that is faster to make and review manually |
| Repository migrations with clear per-step gates and rollback boundaries | Work requiring continuous interactive product or UX decisions |
| Repeated implementation campaigns where each PR builds on the previous merged PR | Changes without meaningful automated tests or substantive CI |
| Work involving ADRs and research spikes whose findings must become precise issue specifications | A very large, indivisible change that exceeds practical review coverage |
| Internal developer tooling, build systems, CI/CD, and infrastructure-as-product work | Repositories where agents cannot access the environment needed to validate completion |
| Campaigns where traceability, retry evidence, and post-mortems matter | Work where the primary bottleneck is deciding strategy rather than supervising execution |

A simple qualification test would be:

1. Is AI-assisted implementation permitted for the destination? If not, stop.
2. Can the work be represented as ordered, independently reviewable issues?
3. Can each issue state concrete acceptance criteria and executable gates?
4. Does the repository have substantive CI and review coverage?
5. Is the repeated supervision cost larger than the cost of setting up the campaign?
6. Can failures safely stop for human intervention rather than forcing autonomous completion?

If the answer is “yes” throughout, shepherd-task may help. If the first answer is “no,” or the work is small, exploratory, weakly tested, or inseparable, it probably will not.
