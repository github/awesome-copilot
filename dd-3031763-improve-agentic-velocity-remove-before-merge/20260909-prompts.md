Materialization then copies each referenced component:

- Skill: the entire referenced skill directory, recursively—including bundled scripts, templates, and data.
- Hook: the entire referenced hook directory, recursively—including `hooks.json` and helper scripts.

Thus, for a conventional plugin, the complete content is determined transitively:

`plugin.json` component references + every file contained within each referenced component directory + plugin-root standard files.

"scripts": [

- Skills generally have a complete-set boundary: everything in the skill directory.
- Most plugins have a declarative component lineup: `plugin.json`.

So `shepherd-task` exposes a real modeling gap: its logical estate is larger than the lineup described by its manifest. A dedicated estate manifest—or moving runtime scripts into a declared skill—would make that membership explicit and machine-verifiable.

Yes. “Agent Plugin” is a formally defined term under the Agent Plugins Specification v1.0.0. An Agent Plugin is a self-contained directory with a root `plugin.json`; portable components are discovered from fixed locations rather than enumerated in the manifest. Version 1 defines exactly two portable component types: skills under `skills/*/SKILL.md` and MCP servers configured by root `mcp.json`. (agent-plugins.org)

This sharpens—and partially corrects—my earlier characterization:

- `plugin.json` is primarily the plugin’s identity and metadata manifest.
- Under the portable spec, it does not list the complete contents or enumerate skills.
- Skills are discovered by scanning the plugin’s `skills/` directory.
- Files such as scripts may exist inside the package, but they are not independently recognized as Agent Plugin components.
- Scripts bundled inside a skill belong to that skill under the Agent Skills model. (agent-plugins.org)

The `extensions.com.github.awesome-copilot` section in this repository’s source manifests is repository-specific build metadata. It tells this repository how to assemble shared source resources into a self-contained plugin directory. It is not the portable Agent Plugins mechanism for enumerating components; the repository removes that composition metadata from the served manifest. The specification expressly permits namespaced client-specific data, but assigns it no portable semantics. (agent-plugins.org)

Consequently, `shepherd-task` is validly an Agent Plugin as a package: it has the required root manifest and contains discoverable skills. Its plugin-root scripts are also valid package files. But, in strict specification terminology, those scripts are not Agent Plugin components. Agent Plugins v1 has no portable “plugin-level scripts” component type and gives those files no automatic execution or discovery semantics. (agent-plugins.org)

The precise characterization is therefore:

`shepherd-task` is an Agent Plugin containing Agent Skills, plus a non-portable plugin-level orchestration runtime implemented as package-local scripts.

GitHub Copilot itself supports additional components—such as agents, hooks, and client integrations—additively around the portable Agent Plugins format. That makes the broader package legitimate for Copilot, but the script-driven control plane remains a Copilot/repository convention rather than something defined by Agent Plugins v1. (docs.github.com)

### 18:47 Response


Yes, but narrowly: it is a gap if the desired capability is portable, plugin-level executable orchestration. It is not necessarily a defect in the specification’s package model.

Agent Plugins v1.0.0 deliberately defines a minimal interoperability floor: skills and MCP servers. It defines the plugin as the entire self-contained directory, so arbitrary files can be packaged, but it assigns no portable discovery or execution semantics to plugin-root scripts. (github.com)

There are two distinct concerns:

┌───────────────────────────────────────────────────┬─────────────────────────────────────────────────────────────────────────┐
│ Concern                                           │ Gap in Agent Plugins v1?                                                │
├───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
│ Include arbitrary scripts in the plugin package   │ No. They are files within the plugin root.                              │
├───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
│ Enumerate every packaged file                     │ No explicit support, but this is primarily packaging/integrity tooling. │
├───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
│ Declare scripts as named commands or entry points │ Yes. No portable component type exists for this.                        │
├───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
│ Define when and how those commands execute        │ Yes. Only MCP server subprocess execution is standardized.              │
├───────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────────────┤
│ Allow a particular client to implement this       │ No. Client extensions are the intended escape hatch.                    │
└───────────────────────────────────────────────────┴─────────────────────────────────────────────────────────────────────────┘

The specification explicitly supports namespaced client extensions for capabilities outside the portable core. A client may define additional manifest data, directories, validation rules, and behavior; other clients may ignore them while the plugin remains conformant. (agent-plugins.org)

Therefore, `shepherd-task` exposes this particular missing abstraction:

A plugin-level command or workflow runtime that coordinates multiple skills, maintains shared state, and exposes executable lifecycle entry points without modeling those entry points as MCP tools.

Whether that should enter the portable specification depends on portability:

- If shepherd-task’s orchestration is inherently GitHub Copilot-specific, a `com.github.copilot` client extension is the correct solution.
- If several agent clients need to install and invoke the same orchestration commands consistently, then it is evidence for a new portable component type—perhaps `commands`, `workflows`, or `runtimes`.

The specification describes itself as a deliberately small interoperability floor, and its public process expects proposed additions to demonstrate a concrete portability requirement and implementer support. There is already public interest in a roadmap beyond skills and MCP, reinforcing that this boundary is recognized, though not yet standardized. (github.com)

So the most accurate conclusion is:

Shepherd-task reveals a deliberate extensibility boundary that becomes a specification gap when cross-client portability of plugin-level orchestration is required.
