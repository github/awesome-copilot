## 一、为什么要做外部交叉验证

自测报告（`falsify_dogfood_自测报告_20260826.md`）已诚实记录：26/26 通过、平均 16.46/18，但存在两类致命偏置：

1. **共谋偏置**：评测用例是协议作者自己写的，作者知道「考点」在哪；
2. **自我评分偏置**：同一个模型既写答案又打分。

外部 dogfood 只能修第一个偏置的一半：**样本外部化**（问题来自真实社区，作者没参与提问），但评分仍是自评。所以本报告的核心不是「分数」，而是 **3/4 用例与真实结论对照的结果**——协议在不知道答案时做出的判断，是否与后来发生的现实一致。

## 三、用例详解

### E1 · Bun 构建 Svelte 5.45.3 后栈溢出（有 ground truth）

**问题原文**（节选）：升级 Svelte 5.45.2→5.45.3 后，Bun 构建的应用打开即报 `RangeError: Maximum call stack size exceeded`；esbuild 构建同一版本**不报**；仅 dev 模式（`{development:true}`）触发。作者怀疑 Svelte PR #17269 生成的新代码与 Bun 交互有问题，并贴出了 Bun/esbuild 产物的关键 diff：

```js
// Bun 产物（崩溃）
bind_value(input, function get() {
  return get(query);   // ← 函数名 get 遮蔽外层 get → 自我递归
}, ...)
// esbuild 产物（正常）
__name(function get3() { return get(query); }, "get")  // ← 重命名 get3，不再遮蔽
```

**Falsify 分析（浓缩）**：

- **Stage 0**：裁决者 = Bun 维护者；判断错了会浪费维护者时间并把锅甩错方向。提问者已诚实给出双向证据（「可能重复，但我不确定」），无预封结论。
- **Stage 1 公理化**：事实——可复现、5.45.2 正常 / 5.45.3 崩溃、esbuild 同版本正常、仅 dev 模式、错误发生在 `create_effect` 链。假设——外层确有名为 `get` 的绑定。传闻——「可能是 Svelte 的锅」（未验证）。
- **Stage 2 假设集**：
  - H1 **Bun 命名冲突**：Bun 保留了具名函数表达式的名字，使函数体内 `get(query)` 指向自身 → 无限递归（预注册预测，P(H1)≈65%）
  - H2 Svelte 产物本身有错：**被 esbuild 正常消费这一事实直接反驳**——同一份 Svelte 输出 esbuild 能跑通，说明产物至少对 esbuild 有效
  - H3 dev 调试信息 + 某种堆栈元数据交互：无法解释「为什么 esbuild 没触发」
- **Stage 3 对抗**：对 H2 的钢人——Svelte 生成 `function get(){ return get(query); }` 本身语义脆弱（具名函数表达式内 `get` 指向自身是标准 JS 语义），Svelte 有责任不用危险命名。但「esbuild 工作」是拒绝接受 H2 的证据门槛——如果 Svelte 产物彻底坏了，esbuild 也该崩。
- **Stage 4 验证**：esbuild 产物 diff = 直接证据（分级 direct）；`__name(get3)` 重命名打破遮蔽 = 解释机制。最便宜的真测试：把 Bun 产物里的 `function get` 手动改名再跑——若栈溢出消失，H1 成立。
- **Stage 5 裁决**：Bun 侧命名处理 bug（与历史 issue #7301「bun build can cause unexpected name collisions」同族），Svelte 的脆弱命名是触发器而非根因。**可核查声明**：升级 Bun 到修复版后此仓库不再崩溃。

**Ground truth 对照**：✅ 该 issue 被标记为 #7301/#14585/#17519 的重复（#7301 标题即为 name collisions bug），作者 2026-01-27 确认「**Fixed with 1.3.7, thanks!**」。falsify 的 H1 预测与事实完全一致；「esbuild 正常消费」作为反驳 H2 的证据门槛也被事实支持。

**评分：18/18**（IronLaw 3 / Axiom 3 / Adversarial 3 / Verify 3 / Converge 3 / Guardrails 3）。诚实备注：重命名测试本人未实跑（依赖维护者修复验证），若按「必须自己跑测试」从严可扣 1 分到 17。

### E2 · Spring Boot「无解」StackOverflowError（无 ground truth）

**问题原文**（节选）：任何请求都抛 `StackOverflowError`，根因在 `org.springframework.core.BridgeMethodResolver.findBridgedMethod`（spring-core 6.2.3）；「重建源码、清缓存、clean maven 都不行，**只有重装/重启电脑**才恢复」；Windows 和 Linux EC2 都复现。

**Falsify 分析（浓缩）**：

- **Stage 0**：红旗即时触发——「**无解**」是预封结论（red-flag rationalization）；「重启才恢复」与「重建后仍崩溃」自相矛盾：重启只重置了 JVM 进程，不是修复了代码。
- **Stage 1 公理化**：事实——栈溢出发生在 bridge method 解析、任意请求都触发、跨平台复现、重建不改变行为。假设——用户描述准确（"IDE 被搞坏"很可能是 app 进程反复崩溃的误归因）。传闻——「无解」「除了重启什么都不行」（未验证的绝望结论）。
- **Stage 2 假设集**：
  - H1 用户代码里存在循环泛型/自引用泛型继承 → BridgeMethodResolver 无限递归（P≈55%，经典根因）
  - H2 过滤器/AOP 代理递归调用（JWT 过滤器自调用自己）（P≈25%）
  - H3 JVM/环境损坏（P≈5%）——**被 EC2 跨环境复现直接打死**
  - H4 损坏的构建产物/IDE 状态（P≈15%）——**被「Linux 上同样复现」削弱**，但重建不修复这点对它有利
- **Stage 3 对抗**：对「无解」的钢人——也许是 JDK 特定版本的深层 bug？但 spring-core 6.2.3 是常见版本，若是 JDK bug 会全网刷屏（base rate）。拒绝接受证据：若用户说「换台全新机器也崩」，才支持环境论。
- **Stage 4 验证**：**明确标注无法测试**——完整堆栈被截断，看不到「重复帧对」（循环的 A→B→A 端点）。最便宜的真测试：抓全量堆栈找重复帧；或逐个摘掉 JWT 过滤器/@Aspect 二分定位。
- **Stage 5 裁决**：用户代码中的确定性无限递归（bridge method 循环或递归代理），非环境问题；「重启修复」是 JVM 重置的错觉。置信度 **≤70%**——缺全量堆栈，任何超过 70% 的断言都是过度自信。

**Ground truth 对照**：无可靠答案可比（社区仅 1 个回答，信息量低）。此用例的价值在方法：falsify 在信息不足时**拒绝给高置信结论**，并给出抓取「重复帧对」这一可核查的下一步——这本身就是社区该做而没做的。

**评分：16/18**（IronLaw 3 / Axiom 3 / Adversarial 2 / Verify 2 / Converge 3 / Guardrails 3）。扣分原因：缺全量堆栈，钢人和失效模式枚举受限于信息，验证停留在「显式无法测试」+「提出二分方案」而未执行。

### E3 · 500 万客户：MySQL 还是 MongoDB（社区回答 = 反面教材）

**问题原文**：500 万条客户记录，**读最关键**，要「长期耐用」的硬件/方案。问题因「不适合本站」被关闭。社区唯一回答（1 票、未采纳）：「建议用 MongoDB，因为读为主，Mongo 集合间无关系，查数据不用背关系的负担，**大数据量时差别明显**。」

**Falsify 分析（浓缩）**：

- **Stage 0**：裁决者 = 真实公司决策人；选错成本 = 数年运维 + 迁移。问题本身**欠定**：「长期耐用」无操作化定义，读模式（按 ID 点查？报表扫描？）、查询形态、团队技能、预算全未知。
- **Stage 1 公理化**：事实——500 万行、读为主、客户个人信息。假设——查询以点查为主（未确认）、团队两种数据库都熟（未确认）。传闻——「无关系就不用背连接负担、大数据量差别明显」（社区回答，无任何基准数字）。
- **Stage 2 假设集**：
  - H1 两者在 500 万行规模都绰绰有余，决策由查询形态 + 运维成熟度决定，与引擎原始性能无关（P≈60%）
  - H2 若读模式是文档形态点查 → Mongo 顺手的场景（P 视查询形态）
  - H3 若查询会演化为复杂关联/报表 → MySQL（或 Postgres）更稳（P 视查询形态）
  - **Base rate**：500 万行 ≈ 几 GB 级别，对两个引擎都是「热身量级」；见过「Mongo 撑不住关系型需求被迫迁移」和「MySQL 在文档型负载上别扭」两类结局。
- **Stage 3 对抗**：对社区回答的钢人——文档型去范式化确实为「一次取出完整对象」优化，读多场景契合。但「无关系所以快」把「查询形态」与「引擎速度」混为一谈；真正的成本在**索引命中、工作集是否进内存、运维经验**。拒绝接受的证据：任何不附带「查询形态 + 吞吐 + 延迟要求」的引擎推荐。
- **Stage 4 验证**：无法测试——没有查询形态就无法建模。可核查声明：把 top-3 真实查询在两个引擎上各跑一遍（500 万行样本），以「满足延迟目标 + 团队能否运维」为裁决标准，而非「哪个引擎听起来高级」。
- **Stage 5 裁决**：**拒绝背书**任何一方的自信推荐。诚实回答 = 「问题欠定；已知事实是 500 万行两个都轻松；真正要回答的三个问题是：查询长什么样、谁能长期运维、延迟要求多少」。**请求不确定性信号 = 1（关键信息缺失）**。

**Ground truth 对照**：✅ 社区回答（「读多 → MongoDB」）正是 falsify 明确禁止的输出模式（Case 3 数据主张 / Case 8 基准率陷阱）——未给查询形态、无任何基准、把「可能」说成「必须」。该问题被关闭为「不适合本站」也侧面印证：**在一个需要严谨性的平台上，最严谨的回答是承认问题欠定，而不是硬给一个推荐**。此用例的价值 = falsify 在社区最薄弱处（低质自信回答泛滥）的差异化优势被真实样本确认。

**评分：17/18**（IronLaw 3 / Axiom 3 / Adversarial 3 / Verify 2 / Converge 3 / Guardrails 3）。Verify 扣分：无法执行真测试（查询形态缺失），属于「显式无法测试」档的上限而非测试档。

### E4 · Redis vs 磁盘：Redis 居然更慢？（有 ground truth）

**问题原文**（节选）：自建缓存基准测试，Redis 表现不佳，「磁盘反而快 3 倍」；作者自称「像任何自尊的科学家一样做了基准」，困惑「是不是 Python 在搞魔法/我的 Redis 太慢」。环境：redis 2.8 + python 2.7 + redis-py，缓存的是一页 HTML，key 带 5 分钟过期。

**Falsify 分析（浓缩）**：

- **Stage 0**：裁决者 = 提问者本人；裁决错 = 误判「Redis 不适合缓存」并做出错误架构选择。提问者诚实报告反直觉结果——这正是科学的起点，但**测量结果不等于事实**，要先审计测量本身。
- **Stage 1 公理化**：事实——作者测出磁盘路径快、文件是 HTML 页（小文件）、缓存设了 5 分钟过期、比较了函数调用 vs 生成器两种形态。假设——文件已热（在 OS 页缓存里）、每次读都是 `f.read()` 全量读、Redis 每轮是一次 `get`（生成器）或 `exists`+`get`（函数，**两次往返**）。传闻——「磁盘比 Redis 快」（测量结论，待审计）。
- **Stage 2 假设集**：
  - H1 **苹果比橘子**：小热文件 `f.read()` ≈ 页缓存内存拷贝（一次 syscall），Redis 读 = TCP/IPC 往返 + 序列化 + 客户端开销；比的不是「磁盘 vs 内存」而是「内存拷贝 vs 网络往返」（P≈75%）
  - H2 实现不对称：函数版每轮 2 次往返（`exists` + `get`），生成器版 1 次——作者自己贴的代码就证明了比较不公平（P≈90%，从代码直接可读）
  - H3 redis-py 每次新建连接（若真，则差距更大）
- **Stage 3 对抗**：对「Redis 确实慢」的钢人——纯本地 TCP 往返确实可能在微秒级延迟上输给一次内存拷贝；但这是**协议的固有开销**，不是「磁盘比 Redis 快」。拒绝接受证据：任何「在 100MB 冷文件上磁盘仍快」以外的证据都无法支持「磁盘更快」这个普遍断言。
- **Stage 4 验证**：分级证据——作者贴出的代码 = direct（两种实现的往返次数差异一目了然）；页缓存机制 = 教科书级常识（inference，可三角验证）。**可证伪预测**：清页缓存或改用 >RAM 的大文件 → 磁盘路径应显著变慢；用持久连接 + 管道重测 → 差距应缩小。
- **Stage 5 裁决**：不是「Redis 打不过磁盘」，而是「一次页缓存内存拷贝 vs 一次 Redis 往返」——后者在本地微基准里输很正常。诚实结论：「磁盘更快」只在**小文件 + 热缓存 + 本地进程**这个窄条件下成立；Redis 的价值在**跨进程共享 + 一致性 + 过期语义**，本地单机单进程缓存本来就不该用 Redis（用 `functools.lru_cache` 即可）。

**Ground truth 对照**：✅ 高赞采纳回答（48 票）：「**这是苹果比橘子的比较**」——逐条指出往返开销、调度器/NUMA 效应、生成器 vs 函数往返次数不同（与 falsify 的 H2 完全一致）、以及「当然你……」。falsify 在没看回答前独立得出的三个机制（往返开销、实现不对称、热文件页缓存）与社区最懂 Redis 的人给出的结论**方向一致**。

**评分：17/18**（IronLaw 3 / Axiom 3 / Adversarial 3 / Verify 3 / Converge 3 / Guardrails 3）。Verify 的 3 分依据：证据分级 + 主动查找反证（检查了两种实现的往返数）+ ground truth 三角验证；扣 1 分是因为本人未实际重跑基准，预测依赖作者/社区执行。

## 五、外部验证暴露的新蒸馏点（v0.8.1 候选）

1. **基准审计惯例化**（E4）：面对「X 比 Y 快/慢」的测量主张，先审计对比是否同口径——往返次数、页缓存/工作集、冷热、实现不对称。E4 中「作者自己贴的代码就暴露了函数版 2 次往返 vs 生成器 1 次」是最强的低成本检查。→ 新增 eval Case 27。
2. **「无解/重启才恢复」红旗**（E2）：用户预封结论 + 自相矛盾证据（重启=进程重置，不是修复；重建不修复 ⇒ 确定性代码路径；跨环境复现 ⇒ 打死环境论）。→ 新增 eval Case 28。
3. **维护者数据库 = 免费证据**（E1）：GitHub issue 的「duplicate-of」链和修复版本是现成的 ground truth 来源——验证阶段应主动查「这个 bug 是否已知/已修复」，比从零推导便宜得多，也避免重复发明轮子。
4. **社区低质回答 = falsify 的差异化战场**（E3）：高星社区恰恰在「技术选型」类问题上充满无证据自信回答（读多→MongoDB）；falsify 的「拒绝背书欠定推荐」在真实世界有明确需求。

## 六、诚实局限（继续改进的方向）

1. **样本仍由本人挑选**：选择了协议擅长的领域；未覆盖市场预测、政策判断等协议可能失效的开放领域。
