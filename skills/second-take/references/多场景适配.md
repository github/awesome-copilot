# 多场景适配：不同 AI 能给我们什么

> 本 skill 是**模型无关（model-agnostic）**的：它审查的是「任何 AI 的推理 / 提示词」，不绑定某一家。
> 同时它天然是**多模型 / 多模态**的——被审查的可以是文本推理模型（Claude、DeepSeek、Gemini、ChatGPT），也可以是图像 / 视频生成模型的提示词（即梦、可灵、Midjourney）。三类适配就是「多模型适配」的体现。
> 核心判断标准只有一个：**那个 AI 有没有把推理过程露出来**。
> 露出来的（A 类）走标准流程；只露摘要的（B 类）改查产物；完全不露的（C 类）改查提示词。
> 界面随时会变，以下按"通常能拿到什么"分类，实际以你看到的为准。

---

## 三类输入形态

| 类 | 代表 | 能拿到 | 我们拿什么当"CoT" | 重拍单形态 |
|---|---|---|---|---|
| **A 有完整推理** | DeepSeek、Claude（extended thinking）、通义千问（思考模式）、Gemini（thinking）、豆包 | UP + 完整思考过程 + 回答 | 思考过程本身 | 模板 A / B（优化与检查指令） |
| **B 只有推理摘要** | ChatGPT（thinking summary） | UP + 推理摘要 + 回答 | **摘要 + 从产物反推** | 模板 A，但结论清单要标注来源 |
| **C 没有推理** | 即梦、可灵、Midjourney、Sora、Runway 等生成类 | 提示词 + 参数 + 产出的图/视频 | **提示词本身** | 模板 C（提示词重拍单） |

---

## A 类：标准流程，不用改

拿到 UP + CoT + 回答，按 SKILL.md 主流程走。

取数方式：DeepSeek 分享链走接口（见 SKILL.md「获取输入」）；Claude 开启 extended thinking 后，思考过程在回复的「思考」区块，直接复制该区块 + 用户提问 + 最终回答即可（Claude 暂无公开分享取数接口，以手动复制为主）；其余平台通常是**用户直接粘贴**——
让他把「我的提问」和「它的思考过程」两段一起贴过来，别只贴回答。

一个提醒：粘贴时最容易漏的是**追加指令**（"再改一下第三段""换个角度"）。追问时确认一下有没有后续轮次。

---

## B 类：只有摘要时怎么办

推理摘要不是 CoT，它是 CoT 的目录。别把它当成完整推理去挑毛病——挑出来的"遗漏"可能是摘要省略的，不是模型没想。

三条调整：

1. **把诊断的主证据从 CoT 换成产物**。摘要只当辅助线索，用作"它大概往哪个方向想了"的提示。
2. **结论清单注明来源**。从产物反推的判断写「由产物反推」，从摘要看出的写「摘要提到」，
   **不许写成"它认为"**——那是把推断当事实，正是我们自己查的"倒置已知"。
3. **诊断里加一句免责**：本轮依据为推理摘要与产物，未见到完整推理过程，结论覆盖度可能偏低。
   这句话要写给用户看，不能藏着。

## C 类：生成类（提示词质检）

### 先分清三样东西：目标、参考、AI 产物

| 类型 | 是什么 | 优先级 | 怎么用 |
|---|---|---|---|
| **目标** | 用户最终想要的样子 | **最高**（极少提供） | 有目标就以它为准，caption 从它反推 |
| **参考** | 用来参考画风 / 构图 / 节奏等元素的素材，或"在此基础上改" | 中，**只取被点名的那一维** | 说清参考的是哪一维，不是全盘照搬 |
| **AI 产物** | 需要修改的、AI 自己生成的 | **不是标准，是被审查对象** | 只回答"哪里不对" |

**怪圈**：拿 AI 产物反推"应该是什么样"，再把这个推出来的当标准去要求生成——
原本的错误被固化成标准，越改越像原来那个错的。

标准来源优先序：**UP 明确要求 > 目标 > 参考中被点名的维度 > 常识与平台默认**。
AI 产物不在其中。UP 没说清又没目标 → **问用户**，不从产物里补齐。
"在此基础上修改"要拆成**继承清单**与**修改清单**两张。

### 输入换成了什么

| 原来的 | C 类对应 |
|---|---|
| UP（用户指令） | **你想要的效果**：口述或写一段"我想让画面/视频是什么样" |
| CoT（推理过程） | **提示词**（它就是模型收到的全部指令，等价于外化的推理） |
| 产物（回答） | 产出的图 / 视频（用户可用文字描述它哪里不对） |
| 参考素材 | 参考图、垫图、seed、风格参考 |

### 检查项怎么映射

| 检查项 | 在提示词上长什么样 |
|---|---|
| 覆盖不全 | 提示词漏了关键要素：主体、动作、环境、时间/光线、景别、镜头运动、风格、画质、比例 |
| 指令冲突 | 提示词内部打架：「写实」又「卡通风」、「极简」又「细节丰富」、「静止」又「运镜」 |
| 表述模糊 | 形容词没操作化：「高级感」「电影感」「氛围感」——模型各画各的 |
| 无据引用 | 用了该平台不认的词：别的平台的参数写法、模型不认识的艺术家/风格名 |
| 倒置已知 | 与平台默认行为冲突：平台默认竖构图却在提示词里写"竖构图"而实际要横版 |
| 版本退步 | **生成类最常踩**：改提示词时把原来对的部分一起改掉，整张图全变 |

### 模板 C：提示词重拍单

```
【想要的画面】
<用户口述的期望效果，原样保留>

【原提示词】
<原文，含参数>

【要素清单】
从原提示词里萃取的成立要素（保留哪些、为什么留）：
1. …
2. …

【必须落实的修改】
1. …
2. …

【输出结构】
1. 改写后的提示词（一整段，可直接粘贴）
2. 参数表（逐项列出，含取值）
3. 负面提示词（negative prompt）
4. 保留项说明（seed / 参考图 / 垫图权重 —— 哪些必须沿用）

【输出要求】
- 只输出上面四项，不要解释为什么这么改。
- 不编造该平台不存在的参数与取值；不确定就写「按你平台当前的写法补」。
- 保留 seed 与参考图：改的是提示词，不是把整张图推翻重来。
```

### 三条硬规矩

1. **不编造平台参数**。即梦、可灵、MJ 的参数语法各不相同，写错等于给一张跑不起来的单子。
   拿不准就写"按你平台当前的写法补"，让用户自己填——这比编一个更像专业的假参数强。
2. **保留 seed 与参考图**。生成类最大的坑是"改一次全变"。重拍单必须明确哪些沿用，
   这与我们"定点修复不推倒重写"是同一条规则，只是对象换成了画面。
3. **改要素，不改全部**。用户说"人物不像"，重拍单只动人物描述与参考权重，
   不要把构图、光线、风格一起重写——那等于 Reshoot 模式，会把他本来就满意的部分一起丢掉。

### 画面怎么描述

生成类任务里，"画面描述"本身有专门规则：四条最高原则（意图优先 / 精炼准确 / 典型性与辨识度 / 写因不写果）、
设定区与描述区的分工（协同不复述）、片段之间无记忆。
写完提示词或 caption 后，用里面的八条判定过一遍。详见 `references/画面描述规范.md`。

### 迭代场景

出图不对 → 改提示词 → 又不对 → 再改。第三轮还在错，就换 Final cut：
不再改提示词，而是**做取舍裁决**——告诉他哪两个诉求在当前模型下不可兼得，选一个。

## 平台清单（按上面三类对号入座）

| 平台 | 类 | 备注 |
|---|---|---|
| DeepSeek | A | 深度思考完整可见；分享链走接口取数 |
| Claude | A | 开启 extended thinking 后「思考」区块即完整 CoT；无公开取数接口，手动复制思考区块 + 提问 + 回答 |
| 通义千问 | A | 思考模式开启时可见推理 |
| Gemini | A | thinking 可见；分享链可用 |
| 豆包 | A | 有思考过程时按 A 处理 |
| ChatGPT | B | 分享快照通常只含推理总结，不含完整 CoT |
| 即梦 | C | 图/视频生成，中文提示词 |
| 可灵 | C | 视频生成为主，提示词 + 参数 + 参考图 |
| Midjourney | C | 英文提示词 + `--` 参数体系，参数语法严格，不得编造 |
| Sora / Runway / Pika 等 | C | 同上，按提示词质检处理 |

**本 skill 跑在哪里（宿主环境）**：second-take 本身是一个 agent skill，装在某个宿主 agent 里（WorkBuddy、Claude Code、Cursor…）。它**审查的是另一个 AI 的输出**——你把从 Claude / DeepSeek / ChatGPT / 即梦等拿到的不满意结果贴进来即可，**重拍单粘回的是「原 AI」，不是宿主**。在 WorkBuddy 里：skill 装在 `~/.workbuddy/skills/second-take`，触发后把其他 AI 的 CoT 贴进来；WorkBuddy 也会展示 agent 自己的思考过程，若你对 WorkBuddy 本体的某次产出不满意，同样可以把那段思考贴进来走诊断。

**判不了一个平台属于哪类，就问用户一句**："它有没有把思考过程显示出来？能贴给我吗？"
比猜好。

**用户确认的保留项**：用户明确认可或指定保留的既有内容属于追加 UP，应列入保留清单；其效力来自用户确认，不来自 AI 曾经生成过。用户认可表达不等于证实其中事实，事实仍须核对。
