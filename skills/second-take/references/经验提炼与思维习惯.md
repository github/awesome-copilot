# 经验提炼与思维习惯

## 结论先行

**对话案例是测试材料，不是知识。** 每次诊断拿到的都是某个具体领域的一段对话，它的作用是暴露机理；机理抽象出来之后，案例本身就该留在原地。

沉淀的顺序固定为：**症状 → 根因 → 机理 → 规则**。跳过抽象直接把案例写进语料，等于把测试集当训练集，规则会带着那个领域的形状。

---

## 一、为什么不把案例写进语料

三害，每一条都会在生产环境里发作：

| 害处 | 表现 | 后果 |
|---|---|---|
| **领域过拟合** | 规则里带着具体名词（某类条目、某张表、某种数值），换领域后模型照着字面套 | 新领域的产物被旧领域的做法带歪 |
| **交叉引用** | 产出里出现「上次那个××」「跟××那版一样」 | 交付物不再自包含；用户没见过那个案例，读完无从判断 |
| **细节泄漏** | 案例里的具体做法被当成通用标准 | 可迁移的部分被不可迁移的部分稀释，规则失真 |

第三点最隐蔽：一条规则里往往机理和做法混在一起，看起来都对，但只有前半段是跨领域成立的。

## 二、抽象规范：案例 → 规则

### 换域测试（唯一判据）

把规则里的专有名词全部替换成占位符，再读一遍：

- **仍成立** → 机理，写进 skill。
- **不成立** → 做法，留在案例文件里。

一句话记忆：**删掉名词还剩什么，什么才是能迁移的。**

### 剥离三步

1. **去名词**：专名、领域术语、具体数值全部拿掉。
2. **换位置描述**：用「某张表」「上一版某条已合格的条目」「其中一类」替代。
3. **补适用边界**：写明这条在什么条件下成立。没有边界的机理容易被过度套用。

### 对照表

| 案例里的发现 | 抽象后（入库） | 留在案例文件 |
|---|---|---|
| 迭代重写后某类条目整条消失 | 定点修复以外的重写会让上一版合格内容一起丢掉 | 那条条目具体是什么 |
| 样例表的字段被两两合并 | 列数限制与字段数冲突时，模型会合并字段而非增列 | 那张表有几个字段、分别叫什么 |
| 为凑体量指标牺牲内容 | 可量化指标会被当考核项去"表演"（reward hacking） | 「3-4 列」「4-6 行」这些具体数字 |
| 某段收尾内容没被写出来 | 结构里没有占位的内容不会被产出 | 那次是几节骨架、那一节叫什么 |
| 模型自行裁决两个冲突要求 | 冲突未点名豁免时，模型会自己选一条，选哪条不可控 | 那次它选对了（运气，不是规律） |

注意最后一行：**「这次裁对了」不是机理，是运气。** 记录结果时只记冲突存在与处置方式，不记运气。

### 语料里的表述规范

- 用「上一版某条已合格的条目」，不用具体条目名。
- 举例一律用占位符：`××项目`、`20XX`、`某张表`、`其中一类`。
- 需要交代来源时用「踩过一次：……」带过，且描述里不含领域名词。
- 不写只能指向单个案例的专有名词：具体条目名、具体表名、具体数值一律不出现。

## 三、存放与隔离

| 内容 | 位置 | 是否公开 |
|---|---|---|
| 抽象后的规则（机理、检查项、硬约束） | skill 目录 | 是 |
| 单次诊断产物、历版指令、试跑记录 | 工作区独立目录 | 否 |
| 原始对话、CoT 原文、用户素材 | 工作区独立目录，且 gitignore | 否 |
| 占位符示意与合成示例 | 可进 skill，但须标注「虚构，仅演示格式」 | 是 |

skill 目录里出现任何真实案例的原文、专名、真实数值，都算污染，回灌时要清掉。

## 四、思维习惯

这些是处理本类任务时固定要走的心智动作，不分领域，每轮都过。

### 诊断时

1. **先还原 UP 链再下判断。** 多轮叠加的指令不还原，就会判错产出目标——把「要最终答案」当成「要改写推理」是最常见的一次性返工。
2. **每条症状追到根因。** 只记症状的规则治不了病：模型删掉一条内容，根因可能是重写、可能是结构没占位、可能是两处清单不同源，三者的改法完全不同。
3. **逐版比对，先查退步再查新错。** 上一版已经解决的问题重新出现，说明上一轮的指令没写进结构，比新错误更值得先修。
4. **CoT 和产物分开看。** CoT 里想好又删掉的内容是自我损耗，不是臆测——它已经算过一遍，只是没落到产物。
5. **长 ≠ 全面，位置靠前 ≠ 成立。** LLM-as-Judge 的长度偏见与位置偏见同样会骗过我们自己。
6. **UP 给了可测量的硬约束就先实测。** 字数、条数、时长这类指标不要采信 CoT 里的估算——估算从来不准，而且模型会估算到"差不多"就宣布达标。自己数一遍，并确认口径（含不含标点、算不算标题）。
7. **先看形态对不对版，再看内容全不全。** UP 点名的文体（要点 / 条目 / 清单 / 问答 / 报告）如果产物形态没对上，内容再全也不合格；而且形态错了会连带让覆盖度判断失真——写成连贯散文时，很难说清"漏了哪一条"。

### 写指令时

8. **每条要求问一遍「它会不会被表演」。** 可计数的就会：加粗几次、几行几列、几条以上。要规定效果与边界，不规定可数动作。
9. **问「结构里有占位吗」。** 只写在修改要点里的内容，大概率不会被产出。
10. **问「这条和另一条打架吗」。** 互相矛盾的约束，模型会任选一条，输出不可控；不可兼得的两组约束（要点全保 + 字数上限）更隐蔽，要额外给取舍优先级。
11. **问「这组约束能不能同时满足」。** 要点全保 + 字数压上限、字段齐全 + 限定列数——不可兼得时，模型牺牲的**总是没被点名的那一维**（通常是句子完整性与语言质量）。凡给上限，必给可删项。
12. **问「同一件事是不是说了两遍」。** 三处重复会让模型把同一件事反复展开。
13. **问「读者读完能不能动手」。** 可行性是最容易被漏掉的一条，因为它不在任何检查项里。

### 交付后

14. **分两堆**：本轮发现里，换领域也成立的回灌 skill；只在当前领域成立的留在案例文件。
15. **能并入既有条目就不新建条目。** 硬约束每多一条，执行时的注意力就被稀释一次。
16. **回灌后跑一遍换域测试。** 确认新增表述里没有残留专有名词，也没有「上次」「那版」这类交叉引用。

## 五、自查清单（每次回灌后过一遍）

1. 这段规则删掉专有名词后，是否仍然成立？
2. 是否夹带了只在单个领域成立的做法？
3. 是否引用了既往案例（「上次」「那版」「跟××一样」）？
4. 举例是否用了占位符，而不是案例原文？
5. 是否写明了适用边界（什么情况下这条成立）？
6. 这条新发现是能并入既有条目，还是必须新建？

任意一条答「否」，先改规则再入库。
