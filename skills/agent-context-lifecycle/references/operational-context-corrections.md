# Reconcile corrections during active work

A user correction changes the approach while preserving the original goal. A status request is not permission to expand diagnostics or retry a disruptive operation.

## Preserve the working baseline

1. Answer briefly with verified state, actual changes and the remaining unknown before more builds or research.
2. Record the user's working baseline with its provenance. Distinguish user-reported success from tool-verified success. Verify only the missing route or behavior; a successful integration does not need complete rediscovery.
3. Choose the smallest relevant check. For an integration, one bounded real exchange can be appropriate if the exact external message is authorized. Fixtures establish only their exercised path. Missing verification means unknown, not broken.
4. Stop unnecessary assistant-created investigations without abandoning the user's objective. Do not update, restart or rewrite a working integration for a hypothetical defect or an upstream/installed version difference alone.

| Evidence | What it establishes | Remaining check, if requested |
|---|---|---|
| User reports receiving a reply | User-reported success for that route | One bounded check of the missing route |
| Identity lookup succeeds | Identity accessible to that credential | Actual delivery and reception |
| Local fixture passes | Exercised parsing/filter path works in the fixture | Live route remains unverified |
| Candidate build passes | Candidate build/test result | Installed version and requested live behavior |

For an authorized messaging probe, resolve the actual recipient through verified metadata, reuse the normal connected path, send one uniquely identifiable non-sensitive message requesting one acknowledgement, and observe real message IDs/logs. Do not simulate a peer and claim end-to-end success. If identity or permission is missing, ask only for that missing input. On failure, inspect the implicated layer. Ongoing autonomous conversation needs its own scope and bounds; it is not a prerequisite for every one-message check.

Consult current official documentation when a capability is in question. Documentation and installed behavior are different evidence. An upstream option does not establish that the installed runtime consumes it and does not authorize an upgrade.

## Late background notifications

A completion notice belongs to an attempt, not necessarily the current state. Match process/session ID and command to chronology. If a failed attempt was superseded by later verified success, say so and do not reopen the incident solely because the old notice arrived late. Probe current state only when freshness or conflicting evidence warrants it.

Do not infer a precise cause from a truncated error. Separate observed failure, verified cause and current state. A manifest check is not installation success; a shell chain ending with a successful print command does not prove earlier checks passed.

## Acceptance scenarios

These describe expected behavior, not completed evaluations:

- **Already works:** preserve the verified/reported route; test the missing route without a broad audit or restart.
- **Only a fixture fails:** label fixture evidence; do not claim live failure or silently patch the runtime.
- **Old installer alert:** correlate attempts and retain later verified success; no automatic retry.
- **Status interruption:** answer now, drop surplus investigation, preserve the goal and any required authority.
